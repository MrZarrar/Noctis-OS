# App-wide libraries and motion audit

2026-10-16. Source audit against `da8b83ce70538b8750aba770e6eb26358aad654c` plus the working files inspected during this session. Recommendations only.

## Verdict and evidence limits

The largest lift is continuity between conversation, panels and finished work, followed by stronger hierarchy in the productivity pages. Use Motion for those transitions, D3 where real timestamps or numerical series support a chart, and locally bundled typography to make the existing visual language consistent. Dependencies are welcome when they improve the result; replacing the existing compositor, native dialogs or Three.js renderers would spend effort without addressing the main gaps.

This report covers all 28 TSX files currently under `apps/web/src/pages/`, including composed views and the dormant Objective list; the Automations placeholder in `App.tsx`; and the requested layout, workbench, surface and UI-package areas. Supporting view helpers were checked for callers and available data. Findings describe source-observable presentation and lifecycle behavior, not a claim that every screen was exercised in a browser. No app server, live Vault, worker, remote desktop session, metered service, build or test suite was started. Phone layouts, frame rates, bundle sizes and actual contrast over the rendered background still need implementation-time measurement.

The checkout changed concurrently during inspection. In particular, Motion, D3 and Lucide are now declared in an unrelated working-tree change to `apps/web/package.json`; they are absent from that file at the commit above. The working lockfile also includes them. No imports of `motion/react` or the three D3 packages were found in the audited page/layout/workbench/surface/UI-package paths. Treat them as provisionally available dependencies, not evidence of an app-wide implementation. The untracked Health work, including components under `apps/web/src/health/`, is ongoing and outside those paths; no `pages/Health.tsx` existed at the final page inventory. Coordinate with that work instead of independently installing a second chart or animation stack.

Metadata supports these candidates; a strict project build remains necessary before adoption. Use the ordinary React 18 APIs, not Motion's React 19.3 view-transition features. D3 functions produce data/path strings; React owns the SVG elements and their lifecycle.

The working manifest already declares the D3 development types: `@types/d3-array@3.2.2` (2025-09-12), `@types/d3-scale@4.0.9` (2025-02-05), and `@types/d3-shape@3.2.0` (2026-08-21). These also predate the cutoff; metadata was checked in their respective npm registry documents. Motion, Sonner and TanStack Virtual carry their own TypeScript declarations.

One lockfile detail needs care: `package-lock.json:2659` resolves `framer-motion@13.5.1`, and `package-lock.json:3518` resolves `motion-dom@13.5.1`; both were published on 2026-10-02 around 12:10 UTC. That is the cutoff calendar day, but later than a conservative midnight-UTC cutoff. For a strict elapsed-time interpretation, an implementation should deliberately lock those two to 13.5.0, published on October 1, rather than claim the current transitive graph satisfies it. `motion-utils@13.5.0` already resolves to October 1. This report changes no resolution and does not recommend an unbounded upgrade. [Framer Motion metadata](https://registry.npmjs.org/framer-motion), [Motion DOM metadata](https://registry.npmjs.org/motion-dom), [Motion Utils metadata](https://registry.npmjs.org/motion-utils).

Keep installation/build-time package retrieval separate from runtime behavior: bundle code, font files and styles into the application; import no CDN entrypoints, cloud examples, telemetry, remote fonts, tiles or hosted widgets. These proposals need no new server. A future implementation should verify an offline load and inspect runtime requests before calling the no-phone-home constraint satisfied.

Do not add a second chart framework alongside D3. A command palette has no demonstrated unmet need here: the rail/tab bar, Conversations and Add panel already expose the relevant entry points. Keep the house Picker and native dialogs. Virtualization is a targeted performance option, not an app-wide visual prerequisite.

### UI package and surface coverage

- **Tokens:** retain depth, spacing, corner and identity semantics (`tokens/depth.ts:2`, `tokens/spacing.ts:2`, `tokens/identity.ts:6`, `tokens/semantic.ts:6`). Reuse the keyed-list and status primitives, prioritizing list selection and evidence provenance. Let detail fields collapse from two columns on compact containers; do not shrink the text. A fallback must stay immediate, understandable and static.
- **Timeline and Verification:** `surfaces/timeline.tsx:14` already establishes a time/marker/body grid, and `surfaces/verification.tsx:23` already groups proven states. Develop these instead of introducing unrelated cards for the today-plan and development references. Keep animation outside payload validation and file-fetch/cache ownership.
