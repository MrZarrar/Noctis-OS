## 1. What Noctis is for

One interface where all of the user's agents (Claude, Codex, Hermes and local models) run and hand
work to each other, on any of the user's machines, reachable from the Noctis phone app. From the phone
the user can start or continue any agent thread on any PC, see the PCs, and open what the agents
produced: scripts, images, videos.

Noctis is the control plane for those agents, not an agent harness. Claude Code and Codex each run
their own loop (tools, context, permissions). Noctis decides where they run, keeps their threads,
gives them shared context (Vault, files), shows their output, and asks the user before consequential
steps.

Example that motivates v1: the Thought Unfolds channel repo lives on the home PC, so a session on the
work PC can't see it. With Noctis, someone switches the home PC on, its node connects, and the user
runs Claude there from work or from the phone, with Codex drawing storyboard frames and a local model
on the same machine, and views the results anywhere.

Noctis is also meant to be beautiful. The intelligence core at the centre of Presence is part of v1
(S6). The other cinematic parts (Jester and NOIR, adaptive Surfaces, focus mode) are deferred, not
dropped (Section 6).

### S1. Fast agent turns

**Status: complete (2026-10-07).** Commits `c9cc2fe` (code) and `329760e` (evidence); see the result
below.

**Problem:** both runtimes start a new process for every turn. Measured on the work PC on 2026-10-07
with Haiku and a trivial reply: a fresh `claude -p` per message took about 6 s; one process kept open
answered follow-ups in 2.4 to 3.4 s. Per-turn spawning adds about 3 s to every message, plus the cost
of reloading the thread.

**Build:**

- Keep one live process per active thread on the node: Claude through the Agent SDK's streaming input
  (one `query()` fed by an async iterable of user messages), Codex through one long-lived
  `codex app-server` per thread.
- Idle timeout closes a thread's process; the next message reopens it with `resume`/`thread/resume`.
- Never `--bare` (it requires an API key).

**Done when:** a test proves the second message in a thread reuses the process, and the status log
records measured first-message and follow-up latency for both runtimes on a real node.

**Result:** `apps/node-agent/src/runtimes/sessions.ts` keeps one process per thread for each runtime.
A turn reuses it only while it is alive, was opened with the same model and roots, and holds the
session the core names; otherwise a new one resumes the stored session. Idle processes close after
10 minutes (`RUNTIME_IDLE_MS`). The gate tests are "THE GATE: the second message in a thread reuses
the process" in `claude.test.ts` and `codex.test.ts`. On the work PC node the same `claude.exe` and
`codex.exe` answered every turn of a thread. Measured, send to completed:

| Setup                                       | Claude first | Claude warm (median) | Codex first  | Codex warm (median) |
| ------------------------------------------- | ------------ | -------------------- | ------------ | ------------------- |
| S1, isolated (no owner settings)            | 1.8 to 2.1 s | 1.23 s               | 3.9 to 5.3 s | 1.22 s              |
| Since 6c3a870, owner's full setup (current) | 5.4 to 6.9 s | 1.94 s               | 5.3 to 13 s  | 1.85 s              |

The status log entries under "v1 scope" in `docs/acceptance/IMPLEMENTATION-STATUS.md` have the full
tables. The problem statement above overstated the saving for the node (Section 8.3).

### S2. Agents hand work to each other through Noctis

**Status: complete (2026-10-07).** Commits `ba1245b` (code) and `d6b52fb` (evidence); see the result below.

**Problem:** when Claude calls Codex from inside its own run, Codex's thread is invisible to Noctis,
can't be continued from the phone, and is stuck on Claude's machine.

**Build:**

- A `noctis_delegate` tool in `noctis-mcp.ts`: `{ runtime, prompt, threadId?, node? }`. Core creates or
  continues a child thread on that runtime and node, waits for the turn, and returns the reply, the
  child `threadId`, and references to any files the child produced.
- Child threads are linked to their parent and visible in the UI; the user can open and continue them.
- Delegation goes through the authority service like any other step.

**Done when:** a Claude thread asks Codex for an image, the image comes back as a viewable output, and a
second request continues the same Codex thread (same `threadId`).

**Result:**

- **The tool.** `noctis_delegate({ runtime, prompt, threadId?, node? })` lives in Claude's in-process
  `noctis` MCP server (`runtimes/claude.ts`), not in `noctis-mcp.ts`: Claude's Noctis tools were
  already hosted in-process, and that is what lets the call wait for an answer. It returns JSON
  with `outcome`, `threadId`, `reply`, `outputs` and, on a refusal, `reason`.
- **The round trip.** The node sends a `delegate` frame on the parent turn's job; the core answers
  with `delegated` (`packages/contracts/src/node.ts`). Nothing listens on the node.
- **Authority.** The core records every delegation as an authority request: `local_reversible_edit`,
  capability `runtime.delegate`, target `runtime:<provider>`, against the parent's job. Policy decides
  as it does for any step: allowed inside an active Objective or under a standing permission,
  otherwise an approval card and a push. A decline refuses the delegation. A delegation still
  waiting when its parent turn ends is declined by `system`.
- **Child threads.** Migration `0010_delegation.sql` adds `parent_thread_id` and `parent_turn_id`.
  A child keeps its parent's identity and Objective, runs on the parent's node and root unless
  `node` names another, and resumes its own session like any thread. A delegation may continue only
  a thread its own parent thread started. `GET /threads/:id` and `GET /threads/:id/children` read
  them, and `conversation.send` takes `threadId`, which is how the owner continues one. A
  follow-up the owner sends without choosing a model stays on the child's last model.
- **Outputs.** Codex's `imageGeneration` item is decoded from its base64 `result`, typed by its
  bytes, posted to `POST /node/outputs` (node credential, only for a job the node holds) and
  recorded as an `output` item with its `attachmentId` and `savedPath`. The turn's result waits for
  those uploads, so the delegation reply carries them. The page loads bytes from
  `GET /attachments/:id/content`, served sandboxed (`content-security-policy: sandbox`).
- **Web.** Chat lists a thread's delegated threads, opens one, continues it, and goes back. An image
  output is drawn inline where the transport can address bytes: the cookie session the phone uses.
  The token transports show it as a line of text.

The gate tests: "THE GATE: a delegated turn runs on a linked child thread, and a second request
continues it" (`conversation.integration.test.ts`), "THE GATE: a turn delegates an image, gets it
back viewable, and continues the same child thread" (`agent.integration.test.ts`, real core and
real agent), and the Chat E2E "a delegation is approved here, opens as its own thread with its
image, and the owner continues it". The live run is in the status log.

### S4. Files and outputs from any machine

**Status: built and verified locally (2026-10-08).** Commits `5cdee68`, `0efe0b0`, `735b830`. The
live done-check waits on the work PC's core being updated and the home PC paired as a node.

**Build:**

- Node capabilities `file.list` and `file.read` on granted roots only (canonicalised paths, symlinks
  resolved, size limits), streamed through core. Video needs range requests.
- Agent turns record the files they create as outputs on the thread (S2 already returns references).
- A viewer in the web app: Markdown and text, images, video, with download.

**Done when:** from the phone, the user opens a script, a storyboard frame and a rendered video that
live on the home PC.

**Result:**

- **Folders.** `file.list` and `file.read` are covered by a `runtime.turn` grant
  (`grantCovers`, `packages/contracts/src/node.ts`): the folders a PC shares with its agents are the
  ones the owner opens, with no second grant to issue.
- **Bytes.** Every listing and range is a job pinned to the node. The node streams the range to
  `POST /node/files`; the core pipes it into the browser's response and stores nothing
  (`apps/core/src/files/gateway.ts`). `GET /files/list` and `GET /files/content` (`Range`,
  `download=1`) serve by extension, sandboxed, with code and markup as plain text.
- **Containment.** The contract refuses a climbing path; the node resolves links and refuses any
  target outside the real root.
- **Page.** Places open as folders; a file opens beside the list, or full screen on the phone.
  Images, video and Download need the cookie session, as S2's images do.
- **Outputs.** Both runtimes already reported `file_change` paths. A turn now offers each written
  file inside a shared folder as "Open <name>", which opens it in Files. Codex's generated images
  stay S2 outputs.

The gates: "THE GATE: lists a shared folder and opens a script, a frame and a video range from the
node" (`agent.integration.test.ts`), `files.test.mjs` (cookie session: a frame draws, a video range
answers 206), and the phone suite's "a shared folder opens and a script in it fills the screen" and
"opens a file an agent wrote straight from the thread it wrote it in".

## 7. v1 definition of done

From the phone, with the home PC switched on and its node connected:

1. Start a Claude thread on the home PC in the Thought Unfolds repo.
2. Claude delegates a storyboard frame to Codex; the frame appears in Noctis; a revision continues the
   same Codex thread.
3. Open the script, the frame and a rendered video from the home PC in the viewer.
4. A step that needs approval arrives as a push notification and is approved from the phone.
5. View the home PC's desktop.
6. Follow-up messages in a thread answer at warm-process speed (S1 numbers recorded). Done in S1;
   recorded under S1 above.

### 8.2 Decisions taken after S1 (owner's instructions)

- **Agents run on the owner's real setup, not in isolation.** Claude loads user, project and local
  settings with every skill (CLAUDE.md, `.claude/skills`, plugins, hooks, MCP servers). Codex uses
  the owner's normal `~/.codex`. This replaces the earlier isolation (`settingSources: []`, Codex
  plugins and MCP servers switched off).
- **The agents' own permission systems do the everyday work.** Claude runs in auto mode
  (`permissionMode: "auto"`, accepted on the subscription). Codex runs `workspace-write` on the
  granted roots with approval `on-request` and the network off.
- **Noctis intervenes only at confirm level** (`isConfirmLevel`: every Section 9.1 class except a
  read and a local edit). For Claude a `PreToolUse` hook stops those calls until the core answers.
  Every ask an agent raises itself is forwarded to the owner and pushed, even a read.
- **No approval waits forever.** An unanswered approval fails the turn after 10 minutes
  (`NOCTIS_APPROVAL_TIMEOUT_SECONDS` on the node overrides) with "approval timed out: ... was not
  answered within ...", that failure is pushed, and the core closes the approval.
- **The classifier** unwraps a leading `powershell -Command`, `pwsh -c`, `cmd /c` or `bash -lc`, so a
  plain read is `read_inspect`; treats constructs that hide what they run (`iex`, `-EncodedCommand`,
  the call operator, dot-sourcing, backticks, `eval`, a mid-command `sh -c`, `node -e`,
  `python -c`) as confirm-level; and treats an MCP tool named for a read as a read.
- **Codex rules.** The node installs `~/.codex/rules/noctis.rules`, so Codex itself prompts before
  recursive deletes, pushing or rewriting git history, and publishing a package. It is the user rule
  layer, so the owner's other Codex sessions prompt for these too.
- **S5 before S4, S3 at home.** The owner reordered the sessions on 2026-10-07 (top of this file)
  and replaced S5's done-check (S5 above).
- **The intelligence core is v1 (S6).** Only Jester and NOIR are deferred; the core and Vesper's
  profile were never meant to be. Added by the owner after reviewing S5.
- **Settings is a gear, not a v1 destination.** It is not in the five, and hiding it behind the flag
  would hide sign-out and turning on push, so it sits at the foot of the rail and in the phone's
  top bar.

- **S2's tool is not in `noctis-mcp.ts`.** That file is Codex's MCP server, a separate process that

### 8.4 Known gaps carried forward

- **Codex has no pre-execution hook.** Noctis sees a Codex action only when Codex asks. The
  `noctis.rules` prompts and Codex's own dangerous-command check cover recursive deletes, history and
  publishing; otherwise the sandbox (writes only in the granted roots, no network) is the
  containment. The owner's Codex plugins and MCP tools are not seen at all.
- **Warm turns are slower with the owner's full setup** (median about 1.9 s against 1.2 s). Planned
  fix: a lean Noctis settings profile (Section 6).
- **MCP read detection is by name prefix.** Planned fix: an explicit allowlist (Section 6).
- **WebFetch and WebSearch are reads**, left to auto mode; a GET can carry data out in its URL.
- **A granted root's own `.claude` settings and hooks run with the owner's authority.** Granting a
  root is the trust decision.
- **Codex writes `trust_level = "trusted"` into `~/.codex/config.toml`** for each root it runs in.
- **This work PC cannot run every check:** no Rust toolchain (`test:desktop`, `rust:*`,
  `build:desktop` are CI's), `test:deploy` refuses to run on the work PC by design, and Node is
  22.23.1 rather than the pinned 22.23.2.
- **Codex cannot delegate yet.** Its Noctis tools run in a stdio child that writes a file and gets
  nothing back. Upgrade path: a reply file the MCP child polls, keyed by delegation id, plus a
  longer `tool_timeout_sec` for that server. Claude delegating to Codex, the v1 case, works.
- **Outside an active Objective every delegation asks the owner,** until a standing permission
  covers `runtime.delegate` for that runtime. The policy is unchanged; this is what it says.
- **A child keeps running when its parent turn ends.** Only a delegation still waiting for approval
  is declined. The child is a visible thread the owner can cancel.
- **Images render inline on the cookie session only.** The token transports (dev browser, Tauri
  shell) cannot attach a credential to an `<img>`, so they show the output as text.
- **S5 was checked in Chrome at a phone's size, not on the owner's phone.** The gate runs at
  400 x 860; iOS Safari's own quirks (the keyboard over the composer, Home Screen safe areas) are
  for the owner to see on the device.
- **The flagged pages keep their old look.** Command, Missions and Artifacts work and sit inside
  the new shell, but were not redesigned.
- **No count on the Approvals tab.** The page lists what is waiting; the tab does not say how many.
  Add one if a push is not enough of a nudge.
- **Threads always follows the newest entry,** even when the owner has scrolled up to read.
- **Threads is still one thread per identity.** The agent and PC are chosen per message; there is
  no list of threads to pick from beyond delegated ones.

### 8.5 Notes after S4

- **Places need a probed agent.** `GET /models` lists a PC's shared folders only for the providers
  it probed, so Files shows nothing for a PC with neither Claude nor Codex, though the file routes
  read the grants directly. Derive the places from the grants if that ever matters.
- **Token transports show text only** in the viewer (the Tauri shell, the dev browser), like S2's
  images. Upgrade path: fetch with the token into a blob URL.

### 8.6 Notes for S3

- A new runtime only has to implement `Runtime` (`runtimes/Runtime.ts`). Delegating to it then
  works as soon as its provider id is accepted: `RUNTIME_PROVIDERS` already lists `hermes`; a
  `local` runtime needs adding there and to the probe.
- The core picks a child's model as: the child thread's last model for that provider, else the
  identity's default if it is that provider, else the first model any connected node offers for it.
- `sink.upload` is available to every runtime, so a local model's files can become outputs the same
  way Codex's images do.
